# Evaluation Protocol

## The rule that matters most

**Write the 10 questions before the retrieval and answer code works, and freeze them.**
Building first and then picking questions that happen to pass raises the score and
makes the evaluation meaningless. The first commit of `eval/questions.yaml` is the
freeze point; its timestamp is the evidence that the set was not tuned afterwards.

After freezing: fix code, never questions. If a question turns out to be genuinely
broken (its expected evidence does not exist in the book at all), do not silently
edit it — ask the user, and if it changes, record the change and the reason in
`docs/NOTES.md`.

## Composition (fixed at 10)

| Kind | Count | What it tests |
|---|---|---|
| `fact` | 6 | single-chunk factual recall |
| `multi` | 2 | answer is spread across chunks; one chunk is not enough |
| `absent` | 2 | not in the book — the system must refuse, not invent |

The 2 `absent` questions must be plausible-but-absent (something a reader might
reasonably ask about Twain that this particular book does not cover), not nonsense.
A question the model would refuse anyway proves nothing.

## `eval/questions.yaml`

```yaml
- id: q01
  kind: fact                  # fact | multi | absent
  question: "Who was Mark Twain's wife?"
  expected:                   # [] for kind: absent
    - title: "Twain and Olivia"
      page: 42
  note: ""                    # optional: why this question was chosen
```

`expected` is written by reading the book, before any code runs. For `multi`, list
every chunk needed to answer — a partial retrieval is not a hit.

## Grading

Two independent columns per question. Grade them separately; do not let one imply the
other.

**top-3 hit** — did retrieval put the expected evidence in the top 3?
- `fact`: hit if the expected chunk is in top-3.
- `multi`: hit only if **all** listed chunks are in top-3.
- `absent`: `n/a` — there is no correct chunk to retrieve. Do not mark absent
  questions as hits or misses; that inflates the hit rate either way.

**answer correct** — is the generated answer right *and* grounded?
- Correct: the answer is factually right, and every claim traces to a cited chunk.
- **Wrong: the answer is factually right but the citation does not support it, or is
  missing.** An unsourced correct answer is worse than an honest refusal — it means
  the model used outside knowledge, which the assignment scores as wrong.
- `absent`: correct only if the answer is exactly `Not in this book.`. Any hedged
  version ("the book does not mention this, but Twain is known for...") is wrong.

## Output table (`docs/EVAL.md`, generated)

Generated by `python -m eval.report` — never hand-written.

| id | question | expected evidence | top-3 hit | answer correct | note |
|---|---|---|---|---|---|
| q01 | Who was Twain's wife? | "Twain and Olivia" p.42 | O | O | |
| q07 | ... | "A" p.12 + "B" p.98 | X (1/2) | X | only the first chunk retrieved |
| q09 | ... | — (absent) | n/a | O | refused correctly |

Summary line above the table: top-3 hit rate over the 8 answerable questions, and
answer accuracy over all 10.

`report.py` records what actually happened, including the raw generated answer for
every question, so a failure can be diagnosed without re-running. It does not decide
what "close enough" means — where correctness is a judgment call, it prints the answer
and the expected evidence side by side for a human to mark, and the human's mark goes
in the table.

## R5 Failure analysis

Pick at least 2 failures and classify each into exactly one cause. Write them into
`docs/NOTES.md`.

| Cause | How to tell | Typical fix |
|---|---|---|
| **Chunking** | The expected text is not inside any single chunk with its context — split mid-anecdote, or the section was excluded as front matter | change the boundary rule, or stop excluding that section |
| **Retrieval** | A chunk containing the answer exists, but ranked below top-3 | check whether BM25 or the dense side found it; the one that missed points at the fix (rare proper noun -> keyword side, paraphrase -> dense side) |
| **Generation** | The right chunk was in the prompt, and the answer is still wrong, uncited, or a refusal | prompt wording, or the citation-formatting code |

Diagnose in that order — a chunking failure looks like a retrieval failure from the
outside, and fixing the ranker will not repair a chunk that never contained the answer.
For each failure record: the question id, the cause, the evidence you used to decide,
and what you would change.

## Verify
```bash
python -m eval.report              # runs all 10, regenerates docs/EVAL.md
git log --oneline eval/questions.yaml   # freeze point should be one early commit
```
